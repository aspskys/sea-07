# 埋点接入研发工作流

埋点接入与开发计划共同执导研发修改业务代码。目标是把埋点接入做成可分期、可审核、可续做的流程。

## 适用场景

- 要把埋点方案落实到服务端、Web、客户端或 HTTP API 代码。
- 埋点事件多，一次性接入改动较多。
- 开始改动代码前，研发需要确认此次改动文档。

## 强制规则

1. 先读埋点方案和开发计划事件，明确本期范围
2. 按照以上信息，整理出工作文档，研发人员确认后，再开始改代码。
3. 只使用 `track_scheme`、`dev_plan_event`、SDK 文档和现有代码作为依据；不猜事件名、属性名、必填规则。
4. 文档和代码必须同步；实现、未完成项、验证结果都要回写文档。
5. 完成标准必须包含实际上报验证, 通过`report_stat`验证上报成果

## 执行顺序

1. 收集资料：项目/环境/端类型/接入方式、埋点方案、开发计划事件、对应端 reference、现有上报代码位置。
2. 拆分范围：明确本期事件、用户属性、非本期项、待确认问题；范围过大先做分期建议。
3. 产出文档：先写“本期埋点接入文档”，
4. 研发确认：需要人查看文档，确认后再开始编码。
5. 实施代码：只改文档中列出的范围，优先复用现有封装。
6. 进行验证：覆盖本地验证、运行验证、上报验证、异常排查。
7. 回写结果：补充实际完成项、未完成项、风险和验证结论。
8. 需要时复核：让第二个 AI 基于文档、diff、验证结果做独立检查。

## 本期文档最小模板

```md
# 本期埋点接入文档

## 1. 背景与目标
## 2. 本期范围
## 3. 事件与属性清单
## 4. 代码落点设计
## 5. 实施步骤
## 6. 验证方案
## 7. 风险与待确认项
## 8. 实际结果回写
```

## 验证检查点

- 事件名、属性名、必填字段是否与方案一致。
- 公共 ID 语义是否统一。
- SDK 初始化、异步 flush、备份日志、重试、优雅退出是否符合要求。
- 是否使用 `big_data report_stat`、`big_data report_storage_issue` 检查接收和入库异常。

## AI 执行约束

- 用户说“做埋点接入开发代码”时，先产出本期文档，再编码。
- 用户只说“查埋点方案”时，可以只获取方案，不强制产出实施文档。
- 用户已经给出本期文档时，以该文档为主补充和续做，不重写另一套计划。
